# 新闻面板、回测验证与因子历史贡献实现汇报稿

## 1. 汇报定位

这次修改的核心，不是单纯“补三个页面”，而是把原来的单次预测系统升级为一个可演示、可解释、可验证的油价风险情报工作台。

旧版 `news-backtest-factor-history-prd.md` 主要写的是规划阶段的方案，包括新闻事件面板、回测验证、因子历史贡献、GDELT/NewsAPI 兜底、数据库缓存、定时任务等。现在代码侧已经完成了面向比赛演示的主体闭环，因此汇报时建议把重点从“方案设想”改成“我们已经如何落地，并且为什么这样改更稳”。

建议主线：

> 我们把系统从“上传文件后给出一次预测”，升级成“首页即可感知风险事件、模型历史可信度和因子驱动逻辑”的工作台。评委不上传文件也能看到系统价值；上传文件后，预测结果还能反哺工作台的最新预测摘要和因子历史记录。

## 2. 新的修改方案总览

本次实现采用“演示稳定优先、真实数据可接入”的方案，而不是一次性把所有外部系统和数据库都强绑定进主流程。

### 2.1 前端修改方案

前端首页已经从原来的单一上传入口，改为 `Oil Risk Intelligence 工作台`：

- `Overview`：展示系统状态、数据更新时间、模型版本、新闻源状态、今日风险摘要。
- `Workstation`：保留原来的上传、预测、结果展示链路。
- `News Events`：展示油价相关新闻事件，支持方向、强度、来源、日期、关键词筛选。
- `Backtest Validation`：展示方向准确率、RMSE、MAPE、区间命中率、预测与实际对比、误差分布、事件标记、阶段表现。
- `Factor History`：展示库存、地缘、宏观、供需、技术五类因子的历史贡献堆叠面积图。

对应代码落点：

- `frontend/src/app/page.tsx`：首页入口改为 `WorkstationLayout`。
- `frontend/src/components/WorkstationLayout.tsx`：新增工作台导航、能力卡片和今日风险摘要。
- `frontend/src/components/NewsPanel.tsx`：新闻事件列表、筛选器、卡片和表格展示。
- `frontend/src/components/BacktestPanel.tsx`：回测指标、走势对比、误差分布、事件标记、阶段表格。
- `frontend/src/components/FactorPanel.tsx`：因子历史贡献堆叠面积图和事件日 tooltip。

### 2.2 后端修改方案

后端新增了一组只读情报接口，统一挂在 `/api/v1` 下，并继续使用原有 `APIResponse` 包络，保证前端调用方式一致。

新增接口：

```text
GET /api/v1/overview
GET /api/v1/events
GET /api/v1/backtest/summary
GET /api/v1/backtest/series
GET /api/v1/backtest/errors
GET /api/v1/factors/history
```

对应代码落点：

- `app/api/routes/events.py`
- `app/api/routes/backtest.py`
- `app/api/routes/factor_history.py`
- `app/api/routes/overview.py`
- `app/services/intelligence_service.py`
- `app/repositories/runtime_intelligence.py`

后端没有让前端直接访问 BigQuery、NewsAPI 或模型服务，而是通过 `IntelligenceService` 统一编排。这样既保护外部凭据，也能保证比赛现场即使外部新闻源不可用，页面仍然有可展示数据或明确状态。

### 2.3 数据接入方案

当前实现采用三层数据策略：

1. 新闻事件：支持 `mock/demo`、`gdelt`、`newsapi`、`hybrid` 四种 provider。
2. 回测验证：优先读取 `data/generated/backtest_Brent_7d.json` 这类离线验证产物。
3. 因子历史：优先读取 `data/generated/factor_history_Brent_7d.json`，并可叠加在线预测产生的新因子点。

这套方案的好处是：

- 演示环境不依赖实时外部服务，稳定性更高。
- 离线回测和因子历史可以通过文件导入，便于赛前反复校验。
- provider 抽象已经留好，后续接 PostgreSQL 或真实定时任务时不需要推翻前端。

相关导入能力：

```text
backend/huaqibei/oil-risk-orchestrator/scripts/import_backtest.py
backend/huaqibei/oil-risk-orchestrator/scripts/import_factor_history.py
backend/huaqibei/oil-risk-orchestrator/app/services/import_service.py
```

## 3. 三个功能模块怎么讲

### 3.1 新闻事件面板

汇报口径：

> 新闻面板解决的是“模型为什么现在要这么判断”的外部事件解释问题。我们没有把新闻当成普通列表，而是把每条事件标准化为方向、强度、置信度、影响行业和标签，让它可以和油价预测逻辑连接起来。

实现亮点：

- 后端统一提供 `GET /api/v1/events`，前端不接触外部密钥。
- 支持按 `impact_direction`、`impact_level`、`source`、日期和关键词筛选。
- GDELT provider 可从 BigQuery 读取油价相关事件并规则化为影响信号。
- NewsAPI provider 可作为 fallback，保证外部主链路不可用时仍有新闻展示。
- `hybrid` 模式先尝试 GDELT，有数据则返回 `hybrid_live`，否则切到 NewsAPI。
- 每条事件都携带 `provider_status`、`analysis_version`、`llm_model_id` 等可解释字段。

演示时可以这样说：

> 这里我们重点规避了一个风险：不让前端直接查 BigQuery。因为那样会暴露云端凭据，也会带来查询费用和延迟。我们的方案是后端统一封装数据源，前端只消费经过清洗和解释的事件信号。

### 3.2 回测验证

汇报口径：

> 回测验证回答的是评委最关心的问题：模型不是只会生成一次预测，它在历史上到底准不准。我们用方向准确率、RMSE、MAPE 和区间命中率四类指标，从方向、误差和风险区间三个角度证明模型可靠性。

实现亮点：

- `BacktestPanel` 同时请求 summary、series、errors 三类接口，页面局部组合展示。
- 顶部指标卡展示方向准确率、RMSE、MAPE、风险区间命中率。
- 核心图表展示实际价格、预测价格和预测区间带。
- 关键事件节点用 ReferenceLine 标注，例如俄乌战争、俄油制裁、巴以冲突、中东冲突升级。
- 误差分布用柱状图展示，阶段表现用表格展示。
- 如果还没有导入真实回测数据，页面不会伪装成有结果，而是显示需要的历史字段，这一点在答辩时可以体现工程严谨性。

演示时可以这样说：

> 这里我们不是只给一个准确率，而是把“预测值是否贴近实际”“方向是否判断正确”“置信区间是否覆盖真实走势”分开展示。这样模型好在哪里、弱在哪里，都能被看见。

### 3.3 因子历史贡献

汇报口径：

> 因子历史贡献解决的是“模型不是黑盒”的问题。原来的结果页只能看到某一次预测的因子贡献，现在可以看到库存、地缘、宏观、供需、技术五类因素如何随时间切换主导权。

实现亮点：

- 新增 `GET /api/v1/factors/history`。
- 前端用堆叠面积图展示五类贡献占比，纵轴按百分比表达。
- Tooltip 同时展示事件标签、7 天预测收益、预测区间、实际收益和是否命中区间。
- `RuntimeIntelligenceStore.record_prediction` 会在成功预测后，把本次预测的 top factors 聚合成五类贡献，并追加到在线历史点。
- 回测页面下方也内嵌了因子历史入口，形成“历史验证 + 解释归因”的连续叙事。

演示时可以这样说：

> 这张图最适合讲故事。比如地缘事件区域突然变大，就能对应战争、制裁、冲突等宏观事件；库存因子变大，则说明市场关注点从地缘风险切回基本面供需。

## 4. 架构决策说明

### 4.1 为什么没有让前端直连外部数据源

这是本次技术方案中最值得强调的设计决策。

前端不直连 BigQuery、NewsAPI 或 LLM，原因是：

- 避免暴露 Google Cloud、NewsAPI、LLM 等外部服务凭据。
- 避免浏览器端承担查询费用和配额风险。
- 避免外部 API 延迟影响页面首屏。
- 后端可以统一做清洗、去重、降级、缓存和结构化解释。
- 前端只面对稳定的业务接口，后续替换数据源不影响 UI。

### 4.2 为什么采用 provider + runtime store

旧 PRD 里提到 PostgreSQL 和定时任务，但比赛演示更需要稳定闭环。本次实现先落了 provider 抽象和运行时/离线数据仓库：

- `DemoProvider`：无外部依赖，保证离线演示。
- `GDELTProvider`：对接 GDELT BigQuery。
- `NewsAPIFallbackProvider`：对接 NewsAPI fallback。
- `HybridNewsProvider`：封装主备切换。
- `RuntimeIntelligenceStore`：读取离线验证产物，并记录上传预测后的最新摘要和因子点。

这样做的价值是：

> 数据库和定时任务仍然可以作为下一阶段接入，但当前版本已经具备完整可演示能力，不会因为外部基础设施未就绪而影响答辩。

### 4.3 为什么回测和因子历史放在同一个故事里

回测回答“模型准不准”，因子历史回答“模型为什么这样判断”。两个模块组合起来，能形成完整闭环：

```text
历史实际走势
  -> 回测指标验证模型可信度
  -> 重大事件标记解释极端行情
  -> 因子历史说明不同时期主导因素
  -> 当前预测结果回到今日风险判断
```

## 5. 建议汇报结构

建议按 5 分钟答辩节奏组织。

### 5.1 开场：一句话说明升级点

> 原系统已经能完成上传数据后的油价预测；这次我们补齐了新闻事件、历史回测和因子历史贡献，把它升级成一个预测、验证、解释、事件监控一体化的油价风险情报工作台。

### 5.2 第一段：首页工作台

要讲的点：

- 评委打开首页，不需要上传文件就能看到系统价值。
- 四个入口分别对应预测、事件、验证、解释。
- 今日风险摘要把高影响事件、最新预测、主导因子放在同一屏。

推荐话术：

> 我们把首页从单一上传入口改成工作台，是为了降低演示理解成本。评委一进来就能看到系统不只是跑模型，还能持续监控新闻事件、展示历史可信度，并解释当前主导因子。

### 5.3 第二段：新闻事件

要讲的点：

- 后端封装 GDELT/NewsAPI，前端不碰密钥。
- 每条新闻变成结构化影响信号。
- 支持方向、强度、日期、关键词筛选。

推荐话术：

> 新闻模块不是新闻聚合，而是事件驱动信号。我们把事件标准化成 bullish、bearish、neutral，以及 impact score 和 confidence，让新闻可以参与油价风险解释。

### 5.4 第三段：回测验证

要讲的点：

- 四个指标：方向准确率、RMSE、MAPE、区间命中率。
- 折线图：实际价格 vs 预测价格。
- 区间带：验证不确定性表达。
- 事件标记：展示极端行情表现。

推荐话术：

> 预测系统只展示结果是不够的，所以我们增加了回测验证。评委可以直接看到模型历史上方向判断、价格误差和风险区间覆盖情况，这比单一准确率更完整。

### 5.5 第四段：因子历史贡献

要讲的点：

- 由单日解释扩展到时间序列解释。
- 五类因子：库存、地缘、宏观、供需、技术。
- 重大事件日 tooltip 能同时看到因子、预测、实际和区间命中。

推荐话术：

> 这部分解决黑盒问题。我们不仅知道模型预测了什么，还能看到不同行情阶段是谁在驱动价格变化。例如地缘事件在冲突阶段变大，库存因子在基本面阶段变大。

### 5.6 收尾：工程稳定性

要讲的点：

- 前端只调后端统一 API。
- 后端有 demo、GDELT、NewsAPI、hybrid provider。
- 离线导入回测和因子历史，保证演示稳定。
- 后续可以平滑接 PostgreSQL、定时任务和更完整 LLM 增强。

推荐话术：

> 我们没有把比赛演示押在实时外部 API 上，而是做了可降级、可导入、可扩展的架构。当前版本能稳定展示，后续接数据库和定时任务时也不需要改前端主体结构。

## 6. 可能被问到的问题与回答

### Q1：为什么不直接让前端查 GDELT？

答：

> 因为 BigQuery 查询需要云端凭据，而且有费用、配额和延迟风险。前端直连也拿不到中文摘要、方向、强度、置信度这些业务解释字段。所以我们把 GDELT 放到后端 provider 里，统一做清洗和结构化输出。

### Q2：NewsAPI 和 GDELT 是什么关系？

答：

> GDELT 更适合做结构化事件源，NewsAPI 更适合做新闻文章 fallback。我们的 `hybrid` 模式优先使用 GDELT，如果 GDELT 不可用或为空，再切换到 NewsAPI，保证比赛现场不空屏。

### Q3：回测数据从哪里来？

答：

> 当前版本支持离线验证产物导入和读取，例如 `data/generated/backtest_Brent_7d.json`。这样可以把模型离线回测结果稳定带到演示环境里。接口层已经固定，后续换成数据库读取不会影响前端。

### Q4：因子贡献是不是随便画的？

答：

> 不是。后端把预测结果里的 top factors 按库存、地缘、宏观、供需、技术五类聚合，并归一化为贡献占比。离线因子历史也按同一结构返回，保证当前解释和历史解释口径一致。

### Q5：如果没有真实外部密钥怎么办？

答：

> 系统不会崩。新闻可以走 demo 或 fallback，回测和因子历史可以读取离线生成文件；页面会通过 `provider_status` 告诉用户当前数据来源和状态。这是为了保证演示稳定性。

## 7. 当前实现与后续增强边界

当前已经完成：

- 工作台式首页和五个主导航。
- 新闻事件接口、筛选器、卡片和表格展示。
- GDELT、NewsAPI、Hybrid provider 抽象。
- 回测 summary、series、errors 三类接口。
- 回测指标卡、走势对比图、误差分布、事件标记、阶段表现。
- 因子历史接口、堆叠面积图、事件 tooltip、历史明细表。
- 离线回测和因子历史导入校验脚本。
- 在线预测后更新首页最新预测摘要和因子贡献点。

后续可以增强：

- 接入 PostgreSQL，把当前 `data/generated` 和运行时数据升级为持久化表。
- 把 `NoOpScheduler` 替换为 APScheduler 或独立 worker，实现 30 分钟新闻刷新。
- 对 GDELT/NewsAPI 结果增加更强的 LLM 中文摘要和行业影响分析。
- 为回测导入增加前端上传入口，而不是只通过 CLI。
- 增加 Playwright 演示脚本，固定首页、新闻、回测、因子历史的答辩点击路径。

## 8. 最终汇报金句

可以用下面这段作为结尾：

> 这次修改让系统从“能预测”变成“能解释、能验证、能监控”。新闻面板提供外部事件依据，回测验证证明模型历史可信度，因子历史贡献解释不同时期的驱动因素。更重要的是，我们用后端 provider 和离线验证产物保证演示稳定，同时保留了接入真实 GDELT、NewsAPI、数据库和定时任务的工程扩展路径。
